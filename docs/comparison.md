# How ISO 20022 libraries handle the conformance suite

The [conformance suite](../conformance/README.md) (45 cases: valid messages, and messages broken in one way each) run against four open-source libraries. Generated by `conformance/compare.py` from the runners in `conformance/runners/`; rerun them to update this page.

This measures one thing: whether a library accepts what it should and rejects what it should, for pacs.008.001.08 and camt.053.001.08. The suite was written alongside Iso20022Kit, so Iso20022Kit passing all of it is expected and proves little; the useful part is what it shows about the others, and new cases from other people are the best way to test Iso20022Kit itself. It is not a ranking of the libraries overall. They differ in scope: some cover hundreds of messages, translate from the old MT format, or check scheme rules (CBPR+, FedNow, SEPA) that this suite doesn't test.

## Libraries and versions

| Library | Version | What "accepted" means here |
|---|---|---|
| Iso20022Kit (.NET) | 0.1.0 (this repository) | `Iso20022.Validate`: official XSD, then business rules. |
| Prowide ISO 20022 (Java) | pw-iso20022 SRU2025-10.4.0 | `AbstractMX.parse`. The open-source edition parses but does not validate (validation is in Prowide's commercial SDK), so here "accepted" means "parsed". |
| Moov iso20022 (Go) | v0.2.1 (latest release; main branch gives the same results) | `document.ParseIso20022Document` then `Validate()`. |
| mx20022 (Rust) | 0.3.0 (crates 0.3.2) | `detect_message_type`, `from_str_in_envelope` into the generated pacs.008.001.08 type, then `validate_message()` (XSD constraints). Has no camt.053.001.08 type (it has 001.11). Its separate scheme validators (FedNow, SEPA, CBPR+) were not run. |

## Findings

Checked against each project's source before being written here.

- **Moov iso20022 rejects valid messages that use an "either/or" account identifier.** In `pkg/pacs_v08`, `AccountIdentification4Choice` declares `Othr` as a non-pointer struct, so a pacs.008.001.08 account given by IBAN fails `Validate()` on the empty `Othr/Id`. In `pkg/camt_v08` both `IBAN` and `Othr` are non-pointer fields, so every camt.053.001.08 account fails one of them. Minimal reproduction: the suite's `pacs008-valid-minimal` (IBAN account) is rejected, while the same message with the account given as `<Othr><Id>…</Id></Othr>`, or with no account, is accepted. The same pattern likely affects other generated choice types; the last commit on the main branch is from January 2023.
- **mx20022 doesn't check minimum/maximum values or date validity.** Its code generator skips `minInclusive`/`maxInclusive` ("require numeric parsing — deferred" in `crates/mx20022-codegen/src/emit/validate.rs`), so a negative `IntrBkSttlmAmt` passes, and `ISODate` is a plain string, so `2026-13-40` passes. It also accepts elements in the wrong order and unknown elements, since it deserialises with serde rather than validating against the XSD. Confirmed on the main branch (October 2026).
- **Prowide's open-source edition is a parser, not a validator.** It accepts every structurally broken message in the suite; its schema validation is part of the commercial edition, which wasn't tested.
- **mx20022 0.3.0 doesn't read a message inside an envelope with an `AppHdr`**: it detects the header's namespace (head.001) instead of the Document's. Its main branch documents that the Document namespace now wins.
- **Every library refuses the two DTD entity attacks** (XXE and "billion laughs") instead of expanding them.
- **Business rules** (totals, statement balances, ISO 4217 decimals, IBAN check digits) are only checked by Iso20022Kit among these runs. mx20022's scheme validators may cover some of them for CBPR+, FedNow and SEPA messages; they weren't part of this run.
